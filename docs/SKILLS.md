# RepoMan skills — how the managers' skills merge into one narrative

RepoMan's agent surface is **pass-through**: each manager keeps its own `SKILL.md`
(testee's, copyroom's, gitman's…). RepoMan does **not** rewrite or merge them. Instead
it adds **one generated entrypoint skill** above them — the single "start here" that
owns the cross-cutting narrative and routes to each manager's own skill.

## The problem with N independent skills

Drop an agent into a repo with several manager skills and, without coordination, you get:

1. **No lifecycle.** Each skill is domain-local and correct in isolation ("route all
   verification through testee", "route all VC through gitman"), but none owns the
   *order* — verify before you integrate, and never integrate on red. That knowledge
   lives *between* the skills, so nobody holds it.
2. **Discovery cost.** The agent must read every skill to learn what's available.
3. **Trigger collisions.** Many skills auto-triggering on overlapping keywords means
   several fire as "primary" and the agent arbitrates badly.
4. **Boilerplate drift.** "Run inside `devenv shell`", the `0/1/2/3` contract, "read the
   structured report" — repeated in every skill, they eventually disagree.

## The principle: separate *narrative* from *detail*

Don't merge the files (that breaks pass-through and couples managers). Add one layer
above them and assign ownership:

| Layer | Owns | Written by |
| --- | --- | --- |
| **RepoMan entrypoint skill** | the *narrative* — lifecycle order, routing, shared law | RepoMan (generated) |
| **Manager skills** (unchanged) | the *detail* — how each domain works | each manager |

This is the `allium-entrypoint` pattern ("Start here… routes to the right skill"),
promoted from one tool's internal router to the **repo's single front door**.

## The entrypoint skill — what it contains

Generated by `repoman install-skills` (run from `repoman-sync`) into
`.agents/skills/repoman/SKILL.md`. The meta-module sets `REPOMAN_SKILLS_DIR` to
`.agents/skills` and offers no option to change it. Four things, nothing more:

1. **The lifecycle spine** — three ordered phases, `change → verify → integrate`, plus
   two unordered activities, `birth / converge` (copyroom) and `docs` (docman). The
   router names only the enabled managers. `change` (the human/agent edit) is always
   present. In a v1 project, `integrate` uses gitman's `describe`, `land`, and `push`.
   In a v2 project, it uses native jj after verification. `scaffold` is
   not a phase, because it happens before the repository exists. `docs` has no place in
   the order.
2. **A routing table** — task → manager → sub-skill → command. A manager gets a row
   only if it is enabled **and** its `<skills_dir>/<skill>/SKILL.md` exists on disk.
   The registry supplies `route_when`; `src/repoman/skills.py` checks the file. Rows and
   the managers line follow the spine first, then the activities.
3. **The law** — run in `devenv shell`, verify before integration, and stop
   integration when verification fails. The v2 router states that native jj owns
   version control. Gitman v2 uses exit code 2 for invalid usage.
4. **Pointers, not copies** — "for detail, open that manager's own skill." Depth stays
   in the sub-skills.

## Why generation matters

The tracked `.repoman/project.toml` roster varies per repo, so a static merged skill
would rot when a manager changes. Templating the entrypoint from the registry (Jinja2,
`templates/entrypoint.SKILL.md.j2`) means:

- every repo gets a **truthful** front door (only installed managers are named — no
  dangling routes);
- the spine names **only enabled** managers (no docs activity without `doc`);
- the nix module (`env.REPOMAN_MANAGERS`), the `repoman` CLI, and the skill all read the
  **same list** — no three-way drift.

Rendered output for `managers = [ "copy" "test" ]`, when both manager skills are
installed. The router lists managers spine-first, so `copy test` renders as `test copy`:

```text
Managers wired in: **test copy**.

## The loop

Run these phases in this order.

    change → verify

## Activities

These activities have no order. Run each one when you need it.

    birth / converge

## Routing — which manager owns what

| When you want to… | Manager | Skill | Command |
|---|---|---|---|
| verify code health, fix lint/format, or rerun failures | test | `testee` | `testee` |
| scaffold a repo, pull template updates, or check template drift | copy | `copyroom` | `copyroom` |
```

The `Laws` section follows the table. The real file also adds an exit-code line and a
pointer to each manager's own skill.

## The contract that makes sub-skills composable

For the merge to hold, manager skills need three small, uniform disciplines (RepoMan
can lint these in `repoman doctor`):

1. **Declare a domain boundary** — "route all *verification* through me." (Most already do.)
2. **Defer cross-domain ordering upward** — a one-line footer: *"For when to verify vs.
   integrate, see the `repoman` skill."* This single edit turns N standalone
   skills into a hierarchy.
3. **Trigger discipline** — sub-skills trigger on *domain* keywords ("test failed",
   "rebase"); the entrypoint triggers on *lifecycle* keywords ("ship it", "what's the
   state of the repo").

## Implementation

- `src/repoman/registry.py` — `Manager.route_when`/`skill`, the `SPINE` phases, and the
  unordered `ACTIVITIES`.
- `src/repoman/skills.py` — `build_spine`, `build_activities`, `render_entrypoint`,
  `install_entrypoint`.
- `src/repoman/templates/entrypoint.SKILL.md.j2` — the template.
- `repoman install-skills` (CLI) — renders + writes the router; called by
  `repoman-sync`. This is the **only** skill RepoMan installs.

## Skill links (the central overlay)

`install-skills` writes the router only. The agent surface is composed in the
central devman overlay at `~/.config/devman` (`.scratch/PLATFORM-INVESTIGATION.md`
§3.3 R3; see also `docs/AGENT-FILES.md`): skills live in the shared pool
`~/.config/devman/skills/`, and each project's central dir links the skills it
should get:

    ~/.config/devman/projects/<p>/agents/skills/<name> -> ../../../../skills/<name>

Each entry has one writer:

- **devman** — curates the pool, the per-project relative symlinks, and the
  project-specific skills that stay real content in the same dir. A person writes
  each link by hand with `ln -s`; `devman-link reconcile` creates none of them.
- **repoman** — generates the router at sync time from the runtime manager roster.

No repo tracks agent skills, and copyroom is not a writer.

`repoman doctor` lints the *link set*, not static copies. The expected set derives
from the roster: `writing` always, each enabled manager's skill, and copyroom's two
sub-skills (`copyroom-adopt`, `copyroom-template-edit`) only when `copy` is enabled.
`gitmanVersion = 2` selects `gitman-v2` in place of `gitman`. The default
keeps `gitman` for existing v1 projects.
devman requires exactly one universal skill, `writing`, and refuses to universalise
`gitman` and `copyroom`. `skill:tool-shipped` checks every expected link.
`skill:genome-overlay` reports the project-specific or overlay skills it cannot judge. A missing link is
a warning, never a gate: the agent surface is developer guidance, not an input to
evaluating a clone.

## Open questions

- **Conflict precedence** when two managers legitimately claim an action (e.g.
  copyroom's `template-test` vs testee's `verify` during a template edit) — the
  entrypoint should name the winner per lifecycle phase rather than let sub-skills
  negotiate.
- **Colliding triggers** — `doctor` already lints the deferral footer (the
  `skill:<key>:defers` rows in `src/repoman/checks.py`). It does not yet lint
  trigger collisions between sub-skills.
